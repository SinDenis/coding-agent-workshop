# Свой кодинговый агент: самостоятельный практикум

Пройди путь от одного запроса к модели до агента, который запускает команды,
исправляет код и согласовывает изменения через Plan Mode. Вся реализация находится
в одном `agent.py`. Каждый тег содержит готовый запускаемый этап.

На каждом шаге переключись на тег, прочитай изменения и запусти пример.
Фрагменты Python ниже показывают ключевую логику, иногда в сокращении:
это части `agent.py`, а не отдельные программы для копирования целиком.

## Подготовка

Нужны Git, uv и macOS/Linux либо Windows с WSL. Python 3.11 установит uv.
Выполняй команды из корня репозитория в одном терминале.

```sh
git status --short
```

Если уже есть свои правки, сохрани их в своей ветке или stash перед переключением.
Не используй `reset --hard` или `clean` для прохождения практикума.
Без переключения файлы можно читать так: `git show step-02-history:agent.py`.

Для запросов к модели создай `.env` по образцу `.env.example`, если его ещё нет,
и заполни `OPENROUTER_API_KEY`. Не перезаписывай существующий ключ и не добавляй его
в Git. Модель выбирается через `OPENROUTER_MODEL`. Запросы платные: заранее задай
лимит отдельного ключа в OpenRouter. Чтение кода и автотесты не требуют ключа.

Shell запускается локально с твоими правами. Это не песочница: используй только
учебный проект без секретов, не настоящие рабочие репозитории.

## 00. Познакомься с проектом

```sh
git switch --detach step-00-start
uv sync --locked
uv run pytest -q
demo_dir="$(uv run python prepare_demo.py)"
uv run python "$demo_dir/tasks.py" --command 'done 1' --command list
uv run python -m unittest discover -s "$demo_dir" -v
```

`demo` содержит исходный трекер. Скрипт создаёт отдельную копию в `.runs/`,
а `demo_dir` хранит её путь. Дальше используй эту же копию: она сохраняется при
переключении тегов. Повторный запуск скрипта создаёт новую копию, ничего не удаляя.
В новом терминале потребуется снова задать `demo_dir` путём к своей копии.

Начальные задачи выглядят так:

```python
[
    {"id": 1, "title": "Купить молоко", "done": False},
    {"id": 2, "title": "Позвонить", "done": False},
]
```

**Результат:** `done 1` ошибочно завершает вторую задачу. Один тест трекера падает.
Это намеренный баг. При этом `uv run pytest -q` проверяет сам агент и инфраструктуру:
эти тесты должны быть зелёными.

Если баг уже исправлен в твоём `demo/tasks.py`, сохрани свои изменения и начни
с чистого клона для повторения примера. Скрипт копирует текущее содержимое `demo`,
а не восстанавливает исходную версию. Поэтому далее агент работает только с копией.

## Часть 1. Агентский цикл

### 01. Один запрос к OpenRouter

```sh
git switch --detach step-01-connect
uv run python agent.py 'Объясни, как посмотреть файлы в терминале'
```

`ask_model()` отправляет HTTP-запрос. Системная инструкция задаёт поведение,
а `messages` содержит сообщение пользователя. Основная часть тела запроса:

```python
{
    "model": os.getenv("OPENROUTER_MODEL", MODEL),
    "messages": [{"role": "system", "content": SYSTEM}, *messages],
    "max_tokens": 4096,
    "reasoning": {"enabled": False},
}
```

Ответ извлекается через `response.json()["choices"][0]["message"]`.
**Результат:** текстовый совет. Модель ещё не видит файлы и не запускает команды.
Один вызов `ask_model()` делает один запрос, а не выполняет целую задачу.

### 02. История диалога

```sh
git switch --detach step-02-history
uv run python agent.py
```

Введи по очереди:

```text
Мой проект называется «Блокнот».
Как называется мой проект?
/quit
```

В `chat()` накапливаем сообщения и передаём их при каждом запросе:

```python
messages.append({"role": "user", "content": question})
response = ask_model(messages)
messages.append(response)
```

**Результат:** второй ответ учитывает первое сообщение. История хранится в списке
Python и пропадает после выхода. Этот внешний цикл ждёт следующую реплику человека;
автоматического цикла работы с инструментами пока нет.

Импорт `readline` обеспечивает редактирование строки, включая Backspace после
русских букв. Проверка `question.encode("utf-8")` отклоняет повреждённый ввод
до записи в историю. Это обработка терминального ввода, не логика модели.

### 03. Описываем инструмент без исполнения

```sh
git switch --detach step-03-tool-schema
uv run python agent.py 'Вызови инструмент shell с командой ls'
```

В запрос добавляется `tools`: описание функции `shell` и схема её аргументов.
Схема указывает, что `command` должна быть строкой:

```python
{
    "type": "object",
    "properties": {"command": {"type": "string"}},
    "required": ["command"],
    "additionalProperties": False,
}
```

Модель может вернуть `tool_calls`. Внутри вызова будет примерно такая функция:

```json
{"name": "shell", "arguments": "{\"command\":\"ls\"}"}
```

**Результат:** программа печатает запрос инструмента, но не список файлов.
Tool call - это данные с просьбой выполнить действие. Сам по себе он ничего
не запускает. Если модель ответила текстом, повтори явную просьбу вызвать инструмент.

### 04. Исполняем команду

```sh
git switch --detach step-04-shell
uv run python agent.py --workspace "$demo_dir" 'Вызови shell с командой ls'
```

`execute_tool()` разбирает аргументы, а `run_shell()` запускает дочерний процесс:

```python
result = subprocess.run(
    command,
    shell=True,
    cwd=workspace,
    stdin=subprocess.DEVNULL,
    capture_output=True,
    text=True,
    errors="replace",
    timeout=30,
    env={key: os.environ[key] for key in ("PATH", "LANG", "LC_ALL") if key in os.environ},
)
```

**Результат:** видны реальные файлы трекера, `stdout`, `stderr` и `exit_code`.
Результат пока увидел только ты. Модель его ещё не получила, поэтому программа
останавливается после исполнения вызова.

### 05. Возвращаем результат модели

```sh
git switch --detach step-05-feedback
uv run python agent.py --workspace "$demo_dir" 'Выполни ls через shell и перечисли увиденные файлы'
```

После сообщения `assistant` с вызовом инструмента добавляем его результат:

```python
messages.append({
    "role": "tool",
    "tool_call_id": call["id"],
    "content": json.dumps(result, ensure_ascii=False),
})
response = ask_model(messages)
messages.append(response)
```

`tool_call_id` связывает результат с конкретным вызовом.
**Результат:** модель отвечает с учётом настоящего списка файлов. Но пока в коде
только два явно написанных запроса. Если второй ответ снова требует инструмент,
программа остановится: третьего запроса здесь ещё нет.

### 06. Собираем агентский цикл и разбираемся с ReAct

```sh
git switch --detach step-06-loop
uv run python agent.py --workspace "$demo_dir" 'Исправь ошибку done: завершается не та задача. Сначала прочитай код и запусти тесты, затем исправь и проверь. Не меняй test_tasks.py.'
```

Заменяем вручную повторённые запросы циклом. Основная логика:

```python
for step in range(1, max_steps + 1):
    response = ask_model(messages)
    messages.append(response)
    calls = response.get("tool_calls") or []
    if not calls:
        return response
    for call in calls:
        result = execute_tool(call, workspace)
        messages.append(tool_result(call, result))
raise RuntimeError("Достигнут лимит шагов")
```

Модель выбирает действие, программа выполняет его и возвращает наблюдение.
Следующее действие выбирается с учётом результата. Это идея **ReAct**:
reasoning + acting, то есть рассуждение о следующем шаге в связке с действием
и наблюдением. Цикл обеспечивает повторение, а tool calling задаёт формат обмена.
Печатать скрытые рассуждения модели для этого не требуется.

**Результат:** агент читает код, воспроизводит баг, исправляет его и запускает тесты.
Проверь самостоятельно:

```sh
uv run python -m unittest discover -s "$demo_dir" -v
```

Все три исходных теста трекера должны пройти; `test_tasks.py` должен остаться
неизменным. Ответ без tool calls завершает текущую работу, но не доказывает,
что задача решена. Лимит 20 запросов - аварийная остановка, не успех.

### 07. Ограничения и обработка ошибок

```sh
git switch --detach step-07-guardrails
uv run pytest -q tests/test_guardrails.py
uv run python agent.py --workspace "$demo_dir" 'Запусти python -m unittest discover -v и сообщи результат'
```

Теперь нельзя принять оборванный ответ за законченный:

```python
if reason not in ("stop", "tool_calls"):
    raise RuntimeError(f"Ответ не завершён нормально: finish_reason={reason}")
```

Также проверяем формат ответа и аргументы инструментов, ограничиваем размер истории
150 000 символами её JSON-представления, а вывод команды - 12 000 байт отдельно
для `stdout` и `stderr`. Завершаем группу процессов команды, чтобы обычные дочерние
процессы не оставались работать после вызова. Ошибки инструмента возвращаем модели,
а обрабатываемые ошибки запроса прерывают текущую работу.

**Результат:** тесты проверяют таймаут, обрезку вывода, неверные аргументы и остановки.
Лимит 20 шагов и таймаут 30 секунд уже были раньше. Обязательный `--workspace`
и запрет выбирать корень репозитория, домашнюю папку или `/` снижают риск выбора
не той папки, но не превращают shell в песочницу.

## Часть 2. Plan Mode

Следующая задача - сохранять задачи между запусками. Сначала согласуем формат,
путь и обработку ошибок, затем меняем файлы. Используем прежний цикл, меняя
инструкции, инструменты и правила перехода к выполнению.

### 08. Планирование только через промпт

```sh
git switch --detach step-08-plan-prompt
uv run python agent.py --plan --workspace "$demo_dir" 'Изучи проект и предложи план сохранения задач между запусками. Пока ничего не меняй.'
```

Добавляем `PLAN_PROMPT`, параметр `mode` и флаг `--plan`. Системное сообщение
выбирается в `ask_model()`:

```python
{"role": "system", "content": PLAN_PROMPT if mode == "plan" else SYSTEM}
```

Промпт просит изучить проект, уточнить требования и предложить план без реализации.
**Результат:** ожидаем текстовый план. Но shell всё ещё доступен, и исполнитель
не запрещает запись. Это промежуточный шаг, а не гарантия неизменности файлов.

### 09. Инструменты только для чтения

```sh
git switch --detach step-09-read-only
uv run pytest -q tests/test_plan.py
uv run python agent.py --plan --workspace "$demo_dir" 'Изучи проект и предложи план сохранения задач между запусками. Пока ничего не меняй.'
```

В режиме планирования доступны `list_files` и `read_file`, а shell отсутствует:

```python
def get_tools(mode):
    if mode not in ("plan", "act"):
        raise ValueError("Неизвестный режим")
    return READ_TOOLS if mode == "plan" else TOOLS
```

Важно не только скрыть shell в запросе, но и проверить разрешения в `execute_tool()`:

```python
allowed = {tool["function"]["name"] for tool in get_tools(mode)}
name = function["name"]
if name not in allowed:
    return {"error": f"Инструмент {name} запрещён в режиме {mode}"}
```

**Результат:** агент читает проект и предлагает план. Неожиданный запрос shell
будет отклонён. Пути проверяются: нельзя читать за пределами рабочей папки,
обращаться к скрытым файлам или обходить ограничения через символические ссылки.
Запускать тесты в этом режиме тоже нельзя: инструмента исполнения команд нет.

### 10. Подтверждаем план и переходим к исполнению

```sh
git switch --detach step-10-approval
uv run python agent.py --workspace "$demo_dir"
```

Внутри диалога введи:

```text
/plan
Добавь необязательный флаг --store PATH. С ним задачи сохраняются в JSON между запусками. Без него оставь прежнее поведение. Если файла нет, начинай с исходных задач. При повреждённом файле возвращай ошибку и не перезаписывай его. Изучи проект и предложи план. Не меняй исходные тесты.
```

В `chat()` теперь есть два состояния:

```python
mode = "act"
plan_ready = False
```

`/plan` очищает историю и включает планирование. После финального ответа в этом
режиме выставляем `plan_ready = True`. Уточняй требования обычным текстом:
каждое уточнение сбрасывает готовность, пока новый ответ не получен успешно.
План хранится в `messages` как текст, отдельного файла или парсера планов здесь нет.

Прочитай предложенный план. Только если согласен, введи:

```text
/approve
```

Команда принимается только в режиме `plan`, когда `plan_ready` истинно.
Затем код переключает режим и добавляет в прежнюю историю подтверждение:

```python
mode = "act"
question = "Подтверждаю последний показанный план. Выполни его и проверь результат."
```

**Результат:** до подтверждения агент только читает. После него получает shell
и реализует согласованное изменение. Слово «согласен» само по себе не переключает
режим. `/cancel` отбрасывает план и возвращает обычный режим без автоматического
исполнения; `/quit` завершает программу.

### 11. Проверяем полный результат

Выйди из агента через `/quit`, затем выполни:

```sh
git switch --detach step-11-rehearsal
uv run pytest -q
uv run python scripts/verify_history.py
uv run python -m unittest discover -s "$demo_dir" -v
uv run python "$demo_dir/tasks.py" --store "$demo_dir/tasks.json" --command 'add Проверить сохранение'
uv run python "$demo_dir/tasks.py" --store "$demo_dir/tasks.json" --command list
```

Последние две команды проверяют реализацию предыдущего шага: добавление и чтение
происходят в разных процессах. Они работают после того, как агент действительно
добавил согласованный `--store PATH`. Если флага нет, вернись к реализации,
а не считай текст «готово» достаточным результатом.

**Результат:** исходные тесты проходят, добавленная задача видна после перезапуска.
`verify_history.py` проверяет каждый учебный тег без API-ключа: стиль, тесты и запуск CLI.
Здесь же добавлены GitHub Actions и дополнительные проверки ответов модели,
но новой механики Plan Mode уже нет.

При желании запусти отдельную автоматическую проверку с реальной моделью:

```sh
uv run python scripts/live_check.py --live --tag step-11-rehearsal --scenario full
```

Это платный прогон на новой копии исходного проекта. Он проверяет исправление бага,
неизменность файлов при планировании, реализацию после подтверждения, сохранение
между запусками и отказ перезаписывать повреждённый JSON. Отчёты остаются в `.checks/`.
Не запускай несколько таких проверок одновременно.

## Что должно получиться

Ты можешь объяснить, где находится системный промпт, почему историю нужно передавать
повторно, чем вызов инструмента отличается от исполнения и зачем после результата
нужен новый запрос к модели. В коде есть цикл с явной остановкой, инструменты,
ограничения и два режима с подтверждением перехода к исполнению.

Смотри изменения через `git show -- agent.py`, сравнивай соседние этапы через
`git diff step-08-plan-prompt step-09-read-only -- agent.py`.
`git switch main` вернёт финальную версию. Для своих доработок создай ветку.
Рабочие копии останутся в `.runs/` и не попадут в Git.
